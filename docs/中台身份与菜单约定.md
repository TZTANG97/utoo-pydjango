# 中台身份与菜单约定

## 1. 身份体系（两套主体，一套 JWT 约定）

| 主体 | 登录入口 | Token 存储 | 后端 |
|------|----------|------------|------|
| 后台员工 | `qd_admin_front` → `POST /api/vue/userLogin.ajax` | Cookie `admin_token` | 网关 `admin_auth`（始终在网关） |
| C 端会员 | `qd_test_front_v3` → `POST /api/auth/login` | Cookie `token` | **网关** `auth_pc`（`qd_svc_auth` 已废弃，勿设 `SVC_AUTH_URL`） |

### JWT / 请求头（两端统一）

两端 axios 拦截器均设置：

- `Authorization: Bearer <token>`
- `token: <token>`（兼容旧 Java 头）

校验：网关 `apps/auth_pc/authentication.py`（及各 svc 的 `auth_support`）认 Bearer / `HTTP_TOKEN` / query。

**密钥**：全仓共用 `config/shared-database.env` 中的 JWT 配置，禁止各服务各写一套密钥。

### 禁止事项

- 前端不得再发明第二套登录态字段名。  
- C 端业务不得绕过 `/api/auth/*` 自建登录接口。  
- 后台菜单权限树不得在前端硬编码完整菜单；以登录后下发的菜单 + [`menu-route.ts`](../qd_admin_front/src/utils/menu-route.ts) 映射为准。

## 2. 菜单与权限

| 端 | 来源 | 说明 |
|----|------|------|
| 管理后台 | 登录接口返回的菜单树（库表 `sy_menu` 等） | 路由映射集中在 `qd_admin_front/src/utils/menu-route.ts`；未映射项进「功能迁移中」 |
| C 端 | 前端路由 + 登录态 | 无后台菜单树；能力开关走运营配置 API |

菜单变更：**改库/后台菜单管理**，不改两端各写一份平行菜单配置（映射表可演进，但权限真相在服务端）。

## 3. 渠道头 `X-Channel`（可选，不拆服务）

用于审计、差异配置、日志，**不作为拆微服务的依据**。

| 值 | 含义 | 谁设置 |
|----|------|--------|
| `admin` | 管理后台 | `qd_admin_front` 请求拦截器 |
| `pc` | C 端 PC Web | `qd_test_front_v3` 请求拦截器 |
| `wx` | 微信相关端 | 微信 H5/小程序请求（若独立壳） |

网关转发微服务时必须透传 `X-Channel`（见 `qd_test_server_django/apps/core/svc_proxy.py` 的 `_FORWARD_HEADERS`）。

服务内读取示例：

```python
channel = request.META.get("HTTP_X_CHANNEL", "").strip().lower() or "unknown"
```

业务差异优先用：**角色 / 租户字段 / 配置表**；`X-Channel` 仅作辅助，禁止 `if channel == "admin": 整套复制逻辑`。

## 4. 完成标准

- 换壳（新前端）不换登录与 JWT 约定。  
- 菜单变更只改中台配置/库表 + 必要的路由映射。  
- 网关与 svc 日志能看到 `X-Channel`。
