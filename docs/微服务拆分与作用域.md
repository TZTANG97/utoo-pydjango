# 微服务拆分与作用域

> **日期**：2026-08-18（§6 于 2026-08-20 修订）  
> **方向与交互（权威入口）**：[大平台与UTOO-方向与交互.md](./大平台与UTOO-方向与交互.md)  
> **取向**：大平台为主；近期同机；业务各自服务各自维护；**方案 B**：中台只提供**基础接口**；菜单/登录产品逻辑在各端 BFF（见 [中台基础能力与各端业务边界-方案B.md](./中台基础能力与各端业务边界-方案B.md)）；按业务拆进程。

推荐（按现在两仓已经在跑的切法，略作收口）：

**8 个 HTTP 进程 + 1 个 Worker。** 不要拆成 20 个。  
同一张表仍然只有一个写进程；青岛 mall **不要**再写库存/资金/发票，改为调已有接口。

---

## 1. 推荐拆成多少个（方便维护、只发有问题的那块）

出问题只重发 **那一个进程**。销售挂了不要动支付；登录改了不要动实验单。

| # | 进程 | 本机端口 | 出问题发谁 | 谁来调 |
|---|------|----------|------------|--------|
| 1 | 青岛网关 | 18080 | 只 admin-web 进不了、路径映射错 | 仅青岛前端 |
| 2 | 愉兔网关 | 18083 | 只 UTOO 网站/小程序进不了、`.ajax` 兼容错 | 仅 UTOO 前端 |
| 2b | 愉兔业务 utoo_biz | 18093 | UTOO 独有域接口 | 仅 UTOO |
| 3 | 身份 `platform/identity` | 18110 | 凭证/用户主数据写 | 各端 BFF 调基础接口 |
| 4 | 实验订单 `qd_svc_order` | 18082 | 领用、开测、复测、实验单列表 | 两个网关都转 |
| 5 | 支付 `qd_svc_payment` | 18084 | 付款、回调、余额、扫码 4 接口 | 两个网关都转 |
| 6 | 经营 `mall` | 18092 | 销售/采购/租赁/生产/外仓/售后、欢迎页 | 青岛网关为主；UTOO 一般不调 |
| 7 | 资产 `qd_svc_admin_asset` | 18090 | 数字化、库存、后台资金台账 | 两个网关都转（青岛改调接口，不要在 mall 里再写库存） |
| 8 | 平台 `qd_svc_admin_platform` | 18091 | 会员运营、入驻、发票 | 两个网关都转 |
| 9 | Worker `qd_worker` | 无 HTTP | 异步任务、短信、支付通知积压 | 被支付/订单投递，不对外 |

这就是 **现在 UTOO 已经拆开的那套**，加上青岛自己的网关和 mall。不再新造一批微服务。

**不要单独起进程的（继续当 mall 里的目录，或已并进上面）：**

- mall 仓 `services/sales` 等 20 个文件夹 = 代码边界，不是发版单元  
- mall `services/identity`（登录已 410）  
- 已删/已并：`qd_svc_auth`、`qd_svc_wx`（进支付）、`qd_svc_invoice` / `qd_svc_entry`（进 platform）

以后只有出现「销售发版总拖垮库存」或「EMKU 工厂发版必须和青岛销售错开」时，再从 mall **摘** `production`。不要一次拆光 20 个目录。

## 2. 为什么是 8+1，不是 6 也不是 20

| 单独成进程 | 原因（维护 / 发版） |
|------------|---------------------|
| 两个网关 | 前端 URL 两套；改 `.ajax` 兼容不该重发青岛网关 |
| 身份 | 登录挂了只发身份；两边菜单共用一份 |
| 实验订单 | 状态机最重，两边都调；发版最频繁之一 |
| 支付 | 钱和回调，故障面必须和开单/领用切开 |
| mall | 青岛经营单据和欢迎页，团队已经一个窗口开发 |
| asset | **现网已独立**；库存/资金台账坏了不该重发销售 |
| platform | **现网已独立**（还并了入驻/发票）；开票坏了不该重发库存 |
| Worker | 重启 HTTP 不该丢掉队列里的通知 |

上次曾写「把 asset/platform 收进 mall」——那会变成改库存必须发整个 mall，和「出问题只发那块」相反。现改回：**保留这两个独立写服务，mall 只调接口。**

不拆销售 vs 采购 vs 租赁：同一张订单家族、同一班人改，硬拆会变成改一个审核要跨两个服务发版。

**EMKU 并进来也不等于再拆一套后端。** 见第 2.1 节：它是第三套前端 + 第三渠道，共用身份/库存/生产接口。

## 2.1 查过现有目录之后：真的不用再拆吗？EMKU 怎么办

对照两仓真实结构：

| 仓里看到的 | 实际含义 |
|------------|----------|
| mall `services/` 约 20 个文件夹 | Java 对照用的**代码边界**；`start-dev.ps1` 默认只起一个 mall，目前 url 只挂了 reporting |
| `services/production` 已独立 Django 工程、只写 `fac_*` | **表已经隔离**，随时能升成独立进程，但现在不必起窗口 |
| `qd_svc_identity` 已拒绝 `X-Channel: emku` | 框架预留了工厂渠道，一期故意关掉 |
| UTOO 发版文档写明与 EMKU Runner/目录隔离 | 现在是两套产品两套流水线；目标是 **调同一套接口**，不是复制 identity/order/payment |
| mall `identity` 登录 410 | 不要给 EMKU 再做第四套登录 |

结论：**现在仍然是 8 个 HTTP + Worker。** 为 EMKU 去拆 20 个微服务，维护成本会高于三个前端。

EMKU 并入时加的是「谁来调」，不是「再写一套库」：

```text
UTOO 前端  ──► 愉兔网关  ──┐
青岛 admin ──► 青岛网关  ──┼─► 同一套：身份 / 订单 / 支付 / mall / asset / platform
EMKU 工厂  ──► 工厂网关* ─┘         * URL 若和青岛一样可先共用青岛网关，只改 X-Channel
```

| EMKU 要做的事 | 调哪个已有服务 | 渠道/平台 |
|---------------|----------------|-----------|
| 登录、菜单（工厂角色） | 身份 | `X-Channel: emku`（或 `factory`），`sy_role.type=3` 且菜单 `pt_type` 含 `3` |
| 工厂工单开始/结束/进度 | mall 里的 production 接口（写 `fac_*`） | 同一 JWT |
| 领料/库存 | asset | 不在 mall 再写库存 |
| 检测实验单（若工厂也要看） | 实验订单 | 禁止自己写 `experiment_order` |
| 付款 | 支付 | 禁止自己收回调 |

身份里 `PlatformCode` 今天只有 `"1"` / `"2"`，二期要加 `"3"`，并打开 `emku`/`factory` 渠道。**不要**新建 `qd_svc_emku_identity`。

**唯一建议「以后再拆进程」的一块：production。**  
原因：`fac_orderform` 等已经和销售表分开；EMKU 发版节奏会和青岛销售不同。等工厂真要独立上线，把 mall 里 production 升成第 9 个 HTTP 进程即可，网关多一条 `PRODUCTION_SERVICE_URL`。现在就拆，只是多一个空转窗口。

不要为 EMKU 拆的：销售、采购、租赁、欢迎页、catalog——工厂用不到或只读接口。

## 3. 各进程作用域

### 3.1 青岛网关（mall `gateway`）

**做：** 只给 admin-web 当接入层。校验/透传 `Authorization`、`X-Channel: mall_qd`；**青岛菜单树拼装与 me 聚合**（读 identity 原子数据）；把 `/api/identity/*` 转到身份**基础**接口；`/api/orders/utoo/*` 转到实验订单；`/api/{sales,procurement,...}` 及未单独写的上游转到 `MALL_SERVICE_URL`。  
**不做：** 不写业务表；不在网关实现完整登录状态机；不起本地 identity。  
**多机：** 无状态，可水平加实例。

### 3.2 愉兔网关（`platform/utoo_gateway`）

**做：** UTOO SPA / 小程序的历史路径兼容（`/api/vue/*`、`/api/experimentOrder/*`、`/api/wx/*` 等）；**UTOO 菜单/me 拼装、登录编排**（读 identity 基础接口）；再转到 order/支付/asset/platform。短信、微信一键等经 identity/payment **原子**接口，网关编排或转发。公众号 XML 回调可仍由网关或 payment 承接，但 **必须与扫码轮询共用 Redis**。  
**不做：** 不再本地 twin 一份登录/实验单写；不在网关写 UTOO 独有业务表（→ `utoo_biz`）；上游挂了回 503。  
**多机：** 无状态；回调 URL 打负载均衡稳定入口。

### 3.2.1 愉兔业务 `utoo_biz`（:18093）

**做：** UTOO **独有**后端（官网/小程序、讨论、预约扩展等）。**不做：** 不 twin order/payment；不写青岛经营单。详见方案 B 文档。

### 3.3 身份（`platform/identity`）

**作用域（方案 B）：** 登录/刷新/JWT；用户/角色/部门/菜单主数据 CRUD；角色-菜单 id 原子列表。  
**迁出至各端 BFF：** 完整菜单树、渠道筛选、登录编排、各端 me 聚合。  
**写表：** `sy_users`、`sy_role`、`sy_menu`、`sy_department`（唯一写入口）。  
**不做：** 实验单、支付、销售单；禁止仅一端使用的产品编排接口。

### 3.4 实验订单 `qd_svc_order`

**作用域：** 检测履约全状态机。主单/子单/分包（`order_type` 6/8/9/10）、抢单、样品到达/领用/开测/结束/寄回、复测、咨询评价、实验类目/项目/产品等主数据（订单域用到的那部分）。C 端下单与后台实验管理同一写入口。  
**调用方：** UTOO 前端、青岛 admin-web（经各自网关白名单）。  
**写表：** `experiment_order*`、样品、复测、订单日志。  
**不做：** 不写销售/采购/租赁单；不收微信支付（建单后调支付接口）；不改 `sy_*`。  
**并发：** 领用/抢单用条件更新 + 行锁/版本号，接口带幂等键。

### 3.5 支付 `qd_svc_payment`

**作用域：** 检测费/充值等 **交易动作**：余额/积分扣减、微信预下单、支付回调、支付锁；已并入的微信扫码登录/预约详情/意见反馈 4 个接口。  
**写表：** 支付单、回调流水、与「扣余额」直接相关的账户变动。  
**不做：** 大平台销售收款若另有商户号，也走本服务不同业务配置，不要在 mall 里再写一套微信支付；后台资金 **台账/人工调账** 走 asset，不要和支付回调抢同一张流水表。  
**并发：** 回调必须幂等；锁可放 Redis，入账以数据库为准。

### 3.6 经营聚合 `mall`（:18092）

一个进程，内部按 **域目录** 分工。网关用 `MALL_SERVICE_URL`。库存/资金/发票 **不要在本进程写库**，调 asset / platform 的接口。

| 域模块 | 作用域 | 写表 | 现状 |
|--------|--------|------|------|
| `sales` | 后台 B2B、库存销售 | `order_type IN (1,7)` | 已有写闭环 |
| `procurement` | 自主采购 | `order_type=5` | 已有写闭环 |
| `rental` | 基础租赁；借贷/校准逐步写 | `rent_*`、`loanrent_*` | 基础租赁已写 |
| `production` | 工厂生产进度 | `fac_*` | 子单进度已有 |
| `external_warehouse` | 外仓销售单 | `out_*` 订单侧 | 订单已写 |
| `after_sales` | 售后工单 | `after_sales_*` | 受理/完成已有 |
| `reporting` | 欢迎页、操作日志 | 只读聚合 + 日志 | 已挂 |
| `catalog` | 商品 SKU 分类品牌 | `goods*` | 按覆写进度 |

`inventory` / `finance` / `operations` 目录可以留着对照 Java，**运行时写请求转到 asset / platform**，避免双写。

### 3.7 资产 `qd_svc_admin_asset`（:18090）

**作用域：** 数字化中心、库存（仓/出入库/盘点）、后台资金台账。  
**写表：** `goods_inventory*`、出入库、后台账户台账相关。  
**调用：** UTOO 管理端现网已走这里；青岛 admin-web / mall 要看库存或出库时 **调本服务接口**，不要在 mall 再写这些表。  
**发版：** 库存 bug 只发 asset，不用发 mall、不用发支付。

### 3.8 平台 `qd_svc_admin_platform`（:18091）

**作用域：** 会员运营、入驻、发票（已吸收 `entry` / `invoice`）。  
**写表：** 入驻、发票、运营配置相关。  
**调用：** 两套前端经网关打这里。  
**发版：** 开票/入驻只发 platform。

### 3.9 Worker

**做：** Celery 任务（支付通知、短信、导出、对账补偿）。任务带幂等键。  
**不做：** 不直接对外 HTTP；不绕过域服务写表（应调领域接口或只在该域仓储里写自己的表）。

## 4. 一张表一个写入口（含收口）

共库仍是 `qd_pt_new`。

| 表/表族 | 目标唯一写进程 | 其它进程 |
|---------|----------------|----------|
| `sy_users` / 角色 / 菜单 / 部门 / 登录日志 | 身份 | 只读 JWT 声明或调身份接口 |
| `experiment_order*` / 样品 / 复测 | 实验订单 | 只调订单接口 |
| 支付单 / 微信回调流水 / C 端余额扣减 | 支付 | mall 只读或调支付查询接口 |
| 销售/采购/租赁/生产/外仓/售后订单 | mall 对应模块 | 实验单不是这些表 |
| 商品主数据 | mall `catalog` | 订单服务需要的实验产品主数据仍以订单域已有接口为准，不复制一份商品中心 |
| 仓库库存出入库 | 资产 asset | mall / 订单只调接口 |
| 后台资金台账/人工调账 | 资产 asset | 交易扣款仍支付 |
| 入驻 / 发票 / 会员运营配置 | 平台 platform | mall 不写 |

**禁止：** mall 直连改实验单；身份以外的服务改菜单；支付以外的服务改支付单；mall 与 asset 同时改库存。

## 6. 仓际与同机部署（避免看错）

> **主从与同机**以 [大平台与UTOO-方向与交互.md](./大平台与UTOO-方向与交互.md) 为准（已拍板）。

| 仓 / 进程 | 维护方 | 目标 |
|-----------|--------|------|
| `mall_qingdao_pydjango` 的 gateway / mall / admin-web | 大平台 | 大平台单独服务；主仓 |
| `mall_qingdao_pydjango/platform/*` | 大平台为主 | **共用中台**唯一活跃代码；同机只跑一套 |
| `utoo-pydjango` 愉兔网关 + UTOO 前端 | UTOO | UTOO 单独服务；网关只 BFF，写业务打中台 |
| 愉兔仓内旧 `qd_svc_*` | 观察期对照 | 不与同机中台并行当第二写入口 |
| `mall_qingdao` Java | 只读 | 不改业务 |

**近期上线**：大平台与 UTOO **同一台服务器**；共用走中台 HTTP；各自维护各自单独服务。

本机青岛默认仍可只起 admin-web / 青岛网关 / mall / identity；同机联调再加愉兔网关与 order 等中台进程。不要用把 20 个 `services/*` 目录当默认启动。

## 7. 两台服务器同时改一条数据怎么办

负载均衡只是把 HTTP 分到两台应用。**库还是同一份 `qd_pt_new`。**  
所以「两台机器同时改」和「一台机器上两个请求同时改」是同一个问题，不能靠粘滞会话、本机内存、或每台自己的 Redis 来解决。

错误写法（两台都会成功，后写覆盖先写）：

```text
A 机：SELECT 库存=10 → 内存里 10-1=9 → UPDATE 库存=9
B 机：SELECT 库存=10 → 内存里 10-1=9 → UPDATE 库存=9
结果：扣了两次，库存还是 9
```

正确做法：**让数据库当裁判，一次只成交一笔。** 应用代码只看「更新影响了几行」。

### 7.1 状态类（领用、审核、抢单）——条件更新

```sql
UPDATE experiment_order
   SET status = 已领用, owner = 当前人, version = version + 1
 WHERE id = ?
   AND status = 待领用;
-- 影响行数 = 1 → 成功；= 0 → 别人已经领了，返回明确失败
```

不要先 `SELECT` 再 `if status==待领用 then UPDATE`。两台都会读到「待领用」。

更挤的可以在同一事务里 `SELECT ... FOR UPDATE` 再改（订单仓里已有 `FOR UPDATE` 用法）。谁先拿到行锁谁改，另一个等锁或失败。

### 7.2 数量类（库存、余额）——库内加减

```sql
UPDATE account SET balance = balance - 100
 WHERE user_id = ? AND balance >= 100;
```

用 `balance = balance - 100`，不要把数字拿到 Java/Python 里减完再写回去。行锁会把两台请求排队，余额不会扣成负数。

### 7.3 回调/重复点击——幂等键 + 唯一索引

微信回调、领用连点、两台 Worker 各跑一遍同一任务：用 **业务单号或 request_id** 做唯一约束。

- 第一次插入成功 → 真的入账  
- 第二次插入冲突 → 查已有结果原样返回，**不要当错误再扣一次**

### 7.4 Redis 锁只能减碰撞，不能当账本

两台应用可以共用 Redis 先抢一把锁（减少打到库上的冲突）。锁过期、进程崩溃、没抢到锁就重试时，**上面三条 SQL 规则仍然必须成立**。没有 Redis，库也要能防超卖。

### 7.5 和你们业务怎么对上

| 场景 | 两台同时来 | 谁赢 |
|------|------------|------|
| 青岛、UTOO 同时点领用 | 条件更新 `status=待领用` | 一行成功，另一行 0 行 → 接口失败「已被领用」 |
| 支付回调打到两台 | 唯一索引（商户单号） | 第一次入账，第二次直接返回已支付 |
| 库存出库 | `qty = qty - n AND qty >= n` | 不够的那笔失败 |
| 改用户名/菜单 | 身份服务事务 + 主键 | 后提交的覆盖或按版本号拒绝，缓存写成功后删除 |
| 欢迎页统计 | 只读 | 无写冲突；不要在这里改订单 |

读请求（列表、欢迎页）可以打任意一台。  
写请求必须进 **唯一写那个微服务**（实验单只进 order，扣款只进 payment），由该进程里的事务对库，而不是两套程序对账。

## 8. 数据库挂了怎么办（框架现在就要定）

**并发对账用数据库，不等于「只要有库就万事大吉」。**  
库负责「两台机器改一条谁赢」；库自己也会挂、会慢、会满连接。框架分层如下，不要混：

| 层 | 干什么 | 挂了怎样 |
|----|--------|----------|
| MySQL（共库 `qd_pt_new`，现网是阿里云 RDS） | 订单、库存、余额、组织的**唯一账本** | 写接口必须失败，不能假装成功 |
| Redis | 缓存、短锁、Celery 队列 | 登录 JWT 仍可用；缓存穿透打库；锁退化成库行锁 |
| 应用进程 | 无状态，可多台 | 挂一台，负载均衡摘掉即可 |
| 对象存储 | 文件 | 库还在，列表能开，附件 404 |

### 8.1 禁止的做法

- 库挂了把扣款/领用先写入 Redis，等库好了再对账（钱和单会对不上）。  
- 生产用 SQLite、本机文件、内存当备用账本。  
- 支付回调在库失败时返回成功（微信不再重试，钱丢了）。  
- 库超时还死等、无限重试非幂等的 POST（会变成重复扣款）。  
- 每个应用节点自己一台 Redis/自己一份库。

### 8.2 库挂了或连不上时，接口怎么表现

| 请求 | 正确行为 |
|------|----------|
| 领用、审核、下单、扣库存、改余额 | 立即 **503**（或明确「服务暂不可用」），前端可重试，**界面不能显示成功** |
| 支付回调 | **返回失败**，让微信/渠道按协议重试；入账逻辑必须幂等，库恢复后重试只入一次 |
| 登录发 JWT | 身份也要读库验密码 → 同样 503，不要发「空头令牌」 |
| 菜单/字典（已缓存在 Redis 且未过期） | 可以暂时返回旧缓存；过期或没有缓存 → 503，不要编造菜单 |
| 欢迎页统计 | 失败就失败，不要用错误数字 |

网关已经对上游不可用回 503，各微服务自己的 DB 异常也应变成 503，而不是 500 堆栈或假 200。

### 8.3 运维侧（RDS，现在就能做）

现网已是云 RDS，不要再自建单机 MySQL 当生产。

- **主备 / 多可用区**：主机挂了切备库，应用连接串走 RDS 地址，不要写死某台 IP。  
- **自动备份 + 可恢复到时间点**：误删、写坏可以回。  
- **监控**：连接数、CPU、磁盘、慢 SQL；满连接时先扩池/砍慢查询，不要再加应用节点猛打。  
- 连接池：`节点数 × 每进程连接` 必须小于 RDS 上限。

这些不写在 Python 里，但框架配置要留出：`DB_HOST` 只配 RDS，超时、池大小可配。

### 8.4 应用框架现在就要具备的（写代码时遵守）

1. **超时**：每条 SQL / 每次 Redis 有超时；卡死不能拖垮整个进程。  
2. **短事务**：领用、扣款在一个事务里做完；不要事务里调外部 HTTP。  
3. **重试分读写**：查询可有限次退避重试；领用/支付/回调只允许 **幂等重试**（靠唯一键）。  
4. **先提交库，再发副作用**：短信、IOT、删缓存放在事务成功之后（Outbox / Celery）；库没提交成功就当没发生。  
5. **健康检查拆开**：进程活着（liveness）和「能连上库」（readiness）分开；库挂了负载均衡应摘掉写节点，而不是假活着接单。  
6. **一个域挂了不影响别的**：支付 RDS 慢不该拖死身份（各服务自己的连接池；共库时至少超时隔离）。  
7. **Redis 挂了**：JWT 仍能验；没有缓存就打库；没有 Redis 锁就靠 SQL 条件更新。Celery 发不出去时，HTTP 返回「通知稍后」，**业务状态以已提交的库为准**。

### 8.5 和「两台机器同时改」怎么叠在一起

正常：两台应用 + 一台（主备）RDS → SQL 条件更新判输赢。  
RDS 主挂了：切备库，短中断期间写请求 503，恢复后客户端/微信重试，幂等保证不双扣。  
切库过程中绝不能改成「先写 Redis」。

## 9. 多机、缓存、库（拆服务时必须一起遵守）

- 每个 HTTP 进程无状态，前面可以负载均衡；**不要粘滞 Session**。  
- 应用多实例 **共用一个 Redis 服务**（缓存/锁/Celery 用不同 DB 号）；量大先加内存和主从，再考虑把 Celery Broker 拆出去。  
- 领用、扣款、库存以 **MySQL 条件更新** 为准。  
- 列表分页、按单号/状态/时间建索引；欢迎页统计不要在热路径扫全历史。  
- 上传走 OSS。  
- 微服务之间禁止 import 对方业务包；协作走 HTTP 或队列。  
- 分层：views → services → repositories，SQL 只在 repositories。

## 10. 需要再拍板时怎么记

- 问「要拆成 20 个微服务吗」→ **不要。推荐 8 个 HTTP + Worker。**  
- 问「销售要不要单独进程」→ **现在不要。** 和采购租赁一起在 mall。
